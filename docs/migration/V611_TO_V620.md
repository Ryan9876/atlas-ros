# Migration Guide: Atlas ROS v6.1.1 to v6.2.0

## Scope

V6.2 is an additive reasoning-architecture release. Existing V1-V4 contracts, execution planning, orchestration, adapters, reconciliation, and historical release records remain unchanged. New callers may adopt the `AdaptiveInputProcessingPipelineV62` and `EnhancedReasoningPackageV62` without migrating provider integrations.

## Package identity

- Current production baseline: v6.1.1
- Candidate package: v6.2.0rc1
- Current rollback during candidate validation: v6.1.0 according to the active release state; promotion planning must designate v6.1.1 as the immediate rollback only when Ryan explicitly authorizes v6.2 production promotion.

## Contract changes

### Added

- Reasoning Package contract version 5
- Canonical intent and semantic fingerprint
- Outcome set with primary, secondary, supporting, and competing outcomes
- Intent graph
- Dependency and constraint records
- Domain knowledge context
- Multidimensional confidence profile
- Dynamic risk profile
- Clarification decision
- Reflection result
- Governed planning-memory references
- Adaptive projection decision

### Unchanged

- Capture contracts
- Reasoning Packages V1-V4
- Management Packages V1-V3
- Execution Plans V1-V3
- Orchestration V2
- Reconciliation V2
- Provider adapter contracts

## Adoption sequence

1. Install the v6.2 candidate in a clean environment.
2. Continue loading existing configuration and registries.
3. Instantiate `AdaptiveInputProcessingPipelineV62` for provider-free input processing.
4. Validate the returned package digest.
5. Check clarification, reflection, confidence, risk, and projection gates.
6. Pass only approved current business nodes to the existing canonical execution planner.
7. Continue to require attended authorization before any provider command.
8. Preserve existing readback and reconciliation transactions.

## Mapping from Reasoning Package V4

| V4 field | V5 equivalent |
|---|---|
| normalized intent | `canonical_intent.canonical_text` |
| selected planning model | `planning_model` and `archetype_selection` |
| primary business outcome | `outcomes.primary` and primary graph node |
| current business actions | current checkpoint graph nodes and projection |
| delegated actions | delegated graph nodes |
| conditional actions | conditional graph nodes |
| evaluation/audit context | nonprojectable evidence/reference nodes or provenance |
| confidence dimensions | `confidence_profile.dimensions` |
| coherence result | coherent metadata validator plus `reflection` |
| requires human decision | `requires_human_decision` and `clarification.status` |
| user-facing summary | style-specific `user_facing_summary` |

## Fail-closed migration rules

Do not project or downgrade a V5 package when any of these conditions exists:

- clarification or human review is required;
- a material confidence dimension fails;
- residual risk requires review;
- a hard constraint conflict exists;
- the graph is blocked or invalid;
- reflection has a blocking or review-required finding;
- multiple outcomes would be lost by the target contract;
- dependency or constraint semantics would be discarded materially;
- provider execution is requested without separate authorization.

## Planning registries

V6.2 adds JSON registry files to the package distribution. Deployments that copy package files manually must include:

- `src/atlas_ros/data/planning_archetypes_v1.json`
- `src/atlas_ros/data/domain_packs_v1.json`

Missing registry data causes pipeline construction to fail closed.

## Fingerprint compatibility

V6.2 fingerprints are new and are not expected to equal V4 digests. They are deterministic within the same schema, registry, policy, and memory state. Presentation-style changes do not change the semantic fingerprint. Business-semantic qualifiers such as production or lab scope, downtime, budget, and timing do change it. Control-plane comparison, historical-preservation, provider-readback, authorization, and receipt directives remain retained as constraints, evidence, or normalization provenance but do not change the business semantic fingerprint.

## CloudVision regression

The v6.1.1 CloudVision business output is a mandatory compatibility contract. Migration is unacceptable if the parent, three checkpoints, withheld work, responsibility, routing, clarification state, or provider-write count changes.

## Rollback

Before final promotion, validate:

1. v6.1.1 source and wheel remain available and checksum-valid;
2. v6.1.1 installs in a clean environment;
3. v6.1.1 CloudVision acceptance remains reproducible;
4. no v6.2 data write is required to run v6.1.1;
5. registries and V5 artifacts can be ignored safely by v6.1.1.

Rollback is a release-state action and requires the authority defined by the active release manifest and Decision Log.
